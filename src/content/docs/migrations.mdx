Migrations are plain [Alembic](https://alembic.sqlalchemy.org) revision files under
`database/migrations/` — there's no `alembic.ini`, no `env.py`, and no separate `versions/`
subfolder to navigate; the files live directly where you'd expect them.

## Generating a migration

`aso make:model -m` (or `-a`) generates one alongside the model, from `--fields`. For a change
to an existing table, autogenerate it from the diff between your models and the database:

```bash
aso make:migration add_published_at_to_posts
```

This compares `Model.metadata` (every column every `Model` subclass declares) against the
actual database schema and writes the `upgrade()`/`downgrade()` that gets you from one to the
other. `--empty` skips the diff and gives you a blank `upgrade()`/`downgrade()` to fill in by
hand — for a data migration, or any change autogenerate can't express (renaming a column shows
up as a drop + an add, for example).

```bash
aso make:migration add_published_at_to_posts --empty
```

<Callout type="warning">
Always read a generated migration before running it. Autogenerate diffs the database against
`Model.metadata`, which only contains tables your own `Model` subclasses declare — a table that
exists in the database but isn't modeled that way looks "extra" to the diff, and autogenerate
will happily write a `drop_table(...)` for it. This is the same caution Alembic's own docs give
for any autogenerated migration, not something specific to one field type or command.
</Callout>

## Running migrations

```bash
aso migrate
```

```
Migration table migrated successfully.
```

```bash
aso migrate:status     # which revisions have run
aso migrate:rollback   # undo the last batch
aso migrate:rollback --step=3
aso migrate:fresh      # drop every table and re-run everything from scratch
aso migrate:fresh --seed
```

`--pretend` (on `migrate`/`migrate:rollback`) prints the SQL without running it.

## SQLite batch mode

SQLite can't `ALTER TABLE` the way Postgres or MySQL can — it has no way to drop a column or
change a type in place. Every migration against a SQLite database runs in Alembic's "batch"
mode automatically: a `batch_alter_table` block rebuilds the table (new table, copy the rows,
swap the name) instead of altering it directly. You don't configure this yourself; it only
applies to SQLite, and the generated migration looks the same either way.

## Factories

A factory builds model instances with realistic fake data, for tests and seeding — not
something application code calls:

```bash
aso make:factory PostFactory --model=Post
```

<CodeFile name="database/factories/post_factory.py">
```python
from aso.database import Factory

from app.models.post import Post


class PostFactory(Factory):
    model = Post

    def definition(self) -> dict:
        return {"title": self.faker.sentence(), "body": self.faker.paragraph()}

    def published(self):
        return self.state({"published": True})
```
</CodeFile>

```python
post = await PostFactory.new().create()
posts = await PostFactory.new().count(5).published().create()
user = await UserFactory.new().has_posts(3).create()   # also creates 3 related Posts
```

A factory bypasses `__fillable__` — it sets attributes directly, the same way Laravel's
factories can set a column no form would ever expose (`email_verified_at`, for example).

## Seeders

```bash
aso make:seeder PostSeeder
aso db:seed
aso db:seed --class=PostSeeder
```

<CodeFile name="database/seeders/database_seeder.py">
```python
from aso.database import Seeder

from database.seeders.post_seeder import PostSeeder


class DatabaseSeeder(Seeder):
    async def run(self) -> None:
        await self.call([PostSeeder])
```
</CodeFile>

`db:seed` runs `DatabaseSeeder` by default — call your other seeders from its `run()`, the same
way Laravel's `DatabaseSeeder` does.

## Coming from Laravel

| Laravel | Aso |
|---|---|
| `php artisan make:migration` | `aso make:migration` |
| `php artisan migrate` | `aso migrate` |
| `php artisan migrate:fresh --seed` | `aso migrate:fresh --seed` |
| `php artisan migrate:rollback --step=3` | `aso migrate:rollback --step=3` |
| SQLite's limited `ALTER TABLE` | Handled transparently by batch mode |
| `php artisan make:factory` | `aso make:factory --model=` |
| `UserFactory::new()->count(5)->create()` | `await UserFactory.new().count(5).create()` |
| `$this->call(PostSeeder::class)` | `await self.call([PostSeeder])` |

## Gotchas

- Read a generated migration's diff before running it — autogenerate is a comparison, not a
  guarantee, and the safest habit (reviewing the SQL) carries over directly from Alembic/Django.
- `--empty` for anything autogenerate can't express correctly: renaming a column, a data
  backfill, or a change to a table Alembic can't see as a `Model`.
- A factory's `definition()`/`state()` set attributes directly — unlike `Model.create()`, they
  aren't limited by `__fillable__`, so a typo'd key raises `AttributeError` rather than being
  silently dropped.
